# `platform` module

Installs the in-cluster half of the Preview Platform into a cluster that
**already exists**: ingress, GitOps, metrics and logs. It is deliberately
cluster-agnostic — `infra/local` points it at k3d today, and `infra/aws` will
point the same module at EKS in phase 8.

```
                       ┌──────────────────────────────┐
   http://<host>:8080  │  ingress-nginx (LoadBalancer)│  IngressClass "nginx" (default)
   ───────────────────►│  klipper svclb → node :80    │
                       └───────────────┬──────────────┘
                                       │
        argocd.<domain> ───────────────┼──────────────► argocd-server (insecure, TLS ends here)
        grafana.<domain> ──────────────┼──────────────► grafana
        prometheus.<domain> ───────────┼──────────────► prometheus
        pr-<N>.<domain> ───────────────┘                (created later, by Argo CD)
```

## What it installs

| Release | Chart | Version | Namespace |
|---|---|---|---|
| `ingress-nginx` | `ingress-nginx/ingress-nginx` | `4.15.1` | `ingress-nginx` |
| `loki` | `grafana/loki-stack` | `2.10.2` | `monitoring` |
| `kube-prometheus-stack` | `prometheus-community/kube-prometheus-stack` | `88.2.0` | `monitoring` |
| `argocd` | `argo/argo-cd` | `10.3.2` | `argocd` |

Every version is an input variable with a pinned default. Nothing floats.

Plus, outside the Helm releases:

- the **`previews` AppProject** — shipped inside the Argo CD release as an
  `extraObjects` entry (see *Ordering* below);
- an optional **repository credentials `Secret`** labelled
  `argocd.argoproj.io/secret-type: repository`, created only when
  `github_token` is non-empty. A public repository needs none.

## What it deliberately does not install

The **`ApplicationSet`** that generates one Argo CD `Application` per open pull
request. That belongs to `platform/argocd/` and is applied on top of this
module. The contract between the two is the module's outputs:

```hcl
module.platform.preview_project_name       # -> "previews"
module.platform.preview_project_namespace  # -> "argocd"
module.platform.preview_namespace_pattern  # -> "preview-*"
module.platform.git_repo_url
```

An `ApplicationSet` whose `template.spec.project` does not equal
`preview_project_name`, or whose generated namespace does not match
`preview_namespace_pattern`, will be rejected by Argo CD at sync time.

## Ordering — the parts that are not cosmetic

Terraform parallelises aggressively, so each of these is an explicit
`depends_on` rather than an accident of resource order in the file.

**1. ingress-nginx goes first.** Its chart installs a
`ValidatingWebhookConfiguration` for `Ingress` objects with
`failurePolicy: Fail`. From the moment that webhook object exists, every
`Ingress` creation in the cluster is routed to the controller — so if the
controller is not yet serving, unrelated releases fail with
`failed calling webhook "validate.nginx.ingress.kubernetes.io"`. Installing it
first with `wait = true` and `wait_for_jobs = true` (the cert is generated by a
pre-install Job) removes the race.

**2. kube-prometheus-stack owns the CRDs.** `ServiceMonitor`, `PodMonitor`,
`PrometheusRule` and friends arrive with this chart. Anything that creates one
must be ordered after it. Concretely:

- Argo CD enables `serviceMonitor` for all five of its components →
  `depends_on = [helm_release.kube_prometheus_stack]`.
- ingress-nginx is installed *before* the CRDs exist, so it cannot create its
  own `ServiceMonitor`. Instead it only exposes a labelled metrics Service
  (`preview-platform.io/scrape: ingress-nginx`) and the matching
  `ServiceMonitor` is declared in this chart's
  `prometheus.additionalServiceMonitors`. Same trick for Loki, and
  `additionalPodMonitors` for promtail (whose chart ships no Service at all).

**3. The AppProject is not a `kubernetes_manifest`.** `kubernetes_manifest`
resolves the resource's schema from the API server **at plan time**, so an
`AppProject` would make `terraform plan` fail on a cluster where Argo CD has
never been installed — i.e. always, on a first apply. Shipping it through the
Argo CD chart's `extraObjects` sidesteps this entirely: `helm install` applies
a chart's `crds/` directory before rendering any template, so the `AppProject`
CRD is guaranteed to be registered by the time the object is applied.

The same reasoning is why `kubernetes_manifest` is not used anywhere in this
module. If a future phase needs one, it must target a CRD installed by an
earlier, separately-applied root module — not by the same `terraform apply`.

**4. Loki before kube-prometheus-stack.** Grafana provisions the Loki
datasource at boot; installing Loki first means the Service already resolves
and the datasource is green on first load instead of after a refresh.

## Prometheus and dynamically created namespaces

This is the one setting most likely to be "tidied up" by someone who does not
know why it is there.

Preview namespaces (`preview-pr-42`, …) are created by Argo CD long after
Terraform has finished, so they can never appear in a namespace selector.
kube-prometheus-stack's defaults are the opposite of what this platform needs:
`serviceMonitorSelectorNilUsesHelmValues: true` silently rewrites an empty
selector into `release: kube-prometheus-stack`, which no preview
`ServiceMonitor` will ever carry.

`values/kube-prometheus-stack.yaml.tpl` therefore sets, for service monitors,
pod monitors, probes, scrape configs and rules alike:

```yaml
serviceMonitorSelectorNilUsesHelmValues: false   # stop injecting the release label
serviceMonitorSelector: {}                       # match every monitor
serviceMonitorNamespaceSelector: {}              # ...in every namespace
```

`{}` is not the same as absent: an omitted `namespaceSelector` means *the
Prometheus object's own namespace*, an empty one means *all namespaces*.

Verify on a live cluster with:

```bash
kubectl -n monitoring get prometheus -o yaml | grep -A3 serviceMonitorNamespaceSelector
```

## Fitting on a laptop

The host runs the platform *and* the previews, so the stack is trimmed rather
than defaulted:

- Prometheus retention `6h` / `2GB`, `emptyDir` storage, `walCompression`.
- `kubeControllerManager`, `kubeScheduler`, `kubeProxy` and `kubeEtcd` scrape
  targets are **disabled**: on k3s these run inside the single server process
  with no separately reachable metrics port, so leaving them on produces
  permanently-down targets and a wall of firing alerts. The corresponding
  `defaultRules` are disabled to match.
- Alertmanager stays, but with no persistence.
- Argo CD's Dex and notifications controllers are off.
- Every workload carries a modest `resources.requests`; total requests are
  roughly 2 GiB.
- `nginx_worker_processes` is pinned to `2`. nginx's `auto` reads the **host**
  CPU count and ignores the container's CPU limit, so on a 64-core workstation
  the controller spawns 64 workers, blows through its memory limit on the first
  config reload and dies with `pthread_create() failed (11: Resource
  temporarily unavailable)` followed by `OOMKilled`. This is not theoretical —
  it is what happened on the first apply of this module.

## Grafana

- Anonymous `Viewer` access is on by default (`grafana_anonymous_access`), so
  the dashboards open without a login. Turn it off for anything public.
- Admin password comes from `grafana_admin_password` (default `admin`) and is
  passed through `jsonencode` so a password containing YAML-significant
  characters cannot break the values file.
- `sidecar.dashboards.enabled` with `searchNamespace: ALL`, so a later phase can
  ship dashboards as `ConfigMap`s labelled `grafana_dashboard: "1"` from any
  namespace and Grafana will pick them up with no Terraform change.
- `root_url` includes `external_http_port`. Without it, every Grafana redirect
  drops back to `:80` and the browser lands on Apache instead of the cluster.

## Inputs worth knowing

| Variable | Default | Notes |
|---|---|---|
| `base_domain` | *(required)* | every hostname is a subdomain of it |
| `external_http_port` | `80` | host port mapped to the ingress; only affects Grafana's `root_url` |
| `github_token` | `""` | empty ⇒ no repository Secret (public-repo path) |
| `grafana_admin_password` | `admin` | sensitive |
| `prometheus_retention` | `6h` | |
| `enable_loki` | `true` | `false` drops Loki, promtail and the datasource |

See `variables.tf` for the full list.

## Providers

The module declares `helm` and `kubernetes` but configures neither — the root
module does, from a kubeconfig context. That is intentional: the cluster is
created outside Terraform (`make up` / eksctl / a separate root module), so
resolving it through a data source would make `plan` fail against an empty
state, before anything had a chance to create it.
